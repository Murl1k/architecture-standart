### <a name="_qmphm5d6rvi3"></a>**Решение**

диаграммы:

- [диаграмма контекста](c4-context.png), исходник [c4-context.puml](c4-context.puml)
- [диаграмма контейнеров](c4-containers.png), исходник [c4-containers.puml](c4-containers.puml)

основные решения:

1. функционал депозитов выносится из монолита интернет-банка в новый сервис депозитов на asp.net core (.net 10) с базой ms sql: команда интернет-банка знает .net, ядро подрядчика не меняется, сайт и новый раздел депозитов в веб-приложении вызывают сервис по rest (+R1, +R2, +R5)
2. коды подтверждения заявки выдает отдельный сервис СМС-подтверждений через СМС-шлюз банка, ядро интернет-банка не дорабатывается (+R6)
3. онлайн-каналы, АБС и система кол-центра обмениваются заявками, ставками и статусами через kafka: заявки не теряются, пока получатель недоступен, АБС не получает синхронных вызовов; прием заявок в системе кол-центра делают специалисты команды АБС по java (R3, R4, +R2, +R3, +R10)
4. команда АБС делает в контуре АБС сервис интеграции депозитов на java spring boot, единственную точку обмена онлайн-каналов с АБС: заявки он записывает через процедуры pl/sql с ограничением скорости, ставки и статусы читает из таблицы исходящих событий, поэтому нагрузка на базу АБС предсказуема (R3, +R4)
5. ставки и согласование ставки ведутся в АБС: справочник ставок и очередь онлайн-заявок в клиенте АБС, отдельные разделы бэк-офисов депозитов и кредитов с разделением прав, xls-файлы и письма уходят из процесса (F10, F11, F12, +R7)
6. сервис депозитов хранит копию ставок, персональные ставки и заявки и отвечает из своей базы и кэша без обращения к АБС, поэтому отклик измеряется миллисекундами (P1)
7. веб-приложение интернет-банка и новые сервисы работают в обоих ЦОД за балансировщиком nginx, сессии хранятся в ms sql, базы реплицируются между ЦОД, kafka развернута в двух ЦОД: при сбое одного ЦОД интернет-банк работает во втором (R1, R2, P3, +R11)
8. веб-приложение кэширует справочники для платежей и обновляет их по расписанию, поэтому они загружаются быстрее секунды и меньше нагружают АБС (P2, R3)
9. разделы депозитов собираются из компонентов системы дизайна банка, заявка оформляется в три шага (U1, U2)
10. все соединения шифруются tls, для сервисов готовятся спецификации openapi, для топиков kafka спецификации asyncapi, интеграции проверяются автотестами на тестовом контуре (+R8, S1, S2)

какие команды участвуют:

- команда интернет-банка: раздел депозитов и кэш справочников в веб-приложении, сервис депозитов, сервис СМС-подтверждений, перевод веб-приложения в два ЦОД вместе с подрядчиком
- команда АБС: справочник ставок, формы и процедуры АБС, сервис интеграции депозитов, прием заявок в системе кол-центра
- команда сайта: раздел депозитов и форма заявки
- IT-отдел: kafka, балансировщик, серверы и базы данных в двух ЦОД, подключение СМС-шлюза

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

- доработать ядро интернет-банка силами подрядчика: отклонено, сроки зависят от подрядчика, это противоречит +R5 и +R6
- интернет-банк обращается к АБС синхронно, через api или напрямую в базу: отклонено, база АБС перегружена и масштабируется только вертикально (R3, +R3, +R4)
- вести ставки в отдельном сервисе вне АБС: отклонено для MVP, бэк-офисы и данные о кредитном риске уже в АБС, там проще сохранить разделение доступа
- оставить интернет-банк в одном ЦОД с переключением на резервный: отклонено, на время переключения интернет-банк недоступен, это не выполняет R2

**Недостатки, ограничения, риски**

- команда интернет-банка считает работу в двух ЦОД пока невыполнимой (+R11): работу нескольких экземпляров на платформе подрядчика нужно проверить вместе с подрядчиком, это главный риск сроков MVP
- АБС масштабируется только вертикально: при сбое ЦОД с АБС заявки копятся в kafka, а платежи и открытие депозитов ждут восстановления АБС
- в MVP заявку обрабатывает человек, срок открытия депозита зависит от загрузки бэк-офиса
- kafka новая технология для банка: нужны эксплуатация, мониторинг и обучение IT-отдела
- через kafka передаются персональные данные, нужны шифрование и разграничение доступа к топикам
- платежи по-прежнему работают напрямую с базой АБС, кэш снимает только чтение справочников, перевод платежей нужен отдельным ADR
